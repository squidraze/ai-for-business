# Файл, который собирает ассистент, не доходит — где рвётся цепочка и как файл должен попадать в чат

English version: [file-delivery.md](file-delivery.md).

Пользователь просит отчёт в `.xlsx`. Не приходит ничего — три попытки подряд, за
два дня. Этот документ про две вещи:

1. **Где рвётся сейчас** — блокер на беке, воспроизведён пять раз. Цепочка умирает
   на *первой* гейтящейся команде внутри субагента, так что файл никогда не
   создаётся, не говоря уже о доставке.
2. **Открытый вопрос по контракту** — даже когда файл будет создан, нигде не
   сказано, как он попадает в чат. Клиент не может отрисовать то, для чего нет
   контракта, и мы предпочли бы реализовать ту форму, которую вы задумали, а не
   угадывать.

Ничего из части 1 нельзя починить с клиента: событие, на которое нам нужно было бы
среагировать, просто не публикуется.

---

## Часть 1 — цепочка и место обрыва

```
пользователь: "Gimme report in xlsx"
  └─ task(subagent_type: code-runner)          ← делегация
       ├─ execute("pwd && ls -la && python3 --version")   ← ГЕЙТ №1 — умирает здесь
       ├─ (openpyxl собирает .xlsx)                        ← сюда не доходит
       └─ deliver_file(...)                                ← ГЕЙТ №2 — сюда не доходит
```

Самое первое, что делает песочный субагент, — тривиальный `execute`: проба
`pwd`/`ls`/`python3 --version`. `execute` гейтится, и на этом заканчивается каждая
попытка. `deliver_file` находится двумя шагами дальше и не вызывается ни разу, то
есть функция «доставка файла» ещё ни разу по-настоящему не отрабатывала.

**Проблема не в том, что стоит гейт.** Default-deny на `execute` / `write_file` /
`deliver_file` — осознанно и правильно: durable-артефакт, видимый компании, должен
проходить через человека. Проблема в том, что гейт невозможно пройти: согласование
не поднимается вообще.

### Форма A — интерапт возвращается ошибкой инструмента

Диалог `0a947d85-5334-4491-ba1a-c0e7dca4bc16`, две попытки (13:51 и 14:11
2026-09-04), строки `c47eab02-d528-4288-8e0f-ba59620add8a` и
`d0920d87-4bc2-4331-b2ef-ce72f05a0b09`:

```
Tool 'task' failed: GraphInterrupt: (Interrupt(value={'action_requests': [{'name': 'execute',
'args': {'command': 'pwd && ls -la && python3 --version'},
'description': "Tool execution requires approval\n\nTool: execute\nArgs: {…}"}],
'review_configs': [{'action_name': 'execute',
'allowed_decisions': ['approve', 'edit', 'reject', 'respond']}]},
id='f56c438ad28bc213d594dc9cadcc09ed'),). Do not retry blindly — …
```

`GraphInterrupt` — это **управляющий поток LangGraph, а не ошибка**. Его поймали
внутри обёртки `task` и сериализовали в строку результата инструмента вместо того,
чтобы дать всплыть к родительскому графу. Следствия по порядку: ран не встаёт на
паузу → нет строки `AIPendingAction` → нет события `ai.action.pending` → одобрять
нечего. `GET .../pending` вернул бы пустой список, а `resume` нечего назвать в
`pending_uuid`.

Модель читает собственный текст ошибки и говорит пользователю «approve the sandbox
run if you see a pending approval prompt» — про кнопку, которой не может
существовать.

### Форма B — ран замолкает и теряет ход

Диалог `d5d653e2-072b-4442-b4a7-369691ecc1d6`, три рана:
`54f8da83-7945-4a53-aee6-3db4e5c5e7da` (12:26),
`4d08af72-7de6-46f8-8ad0-7c1eb5825a69` (13:40),
`c9227f6f-a335-4450-b663-f03bac91db35` (13:42). К последним двум картина свелась к
минимуму:

```
seq 1-3  ai.token      (29 символов «…building the XLSX now»)
seq 4    ai.tool_call  task
         … тишина
```

Результата инструмента не приходит вообще — даже строки `GraphInterrupt` из формы
A. **Терминального события тоже нет**: ни `ai.run.completed`, ни `.error`, ни
`.cancelled`. По контракту стриминга такой ран до сих пор открыт; клиент
выбирается только по собственному 60-секундному watchdog.

И ход **не сохраняется**. Переоткрытый диалог отдаёт строки, заканчивающиеся
сообщением самого пользователя — в ране `54f8da83` это стоило трёх успешных
вызовов инструментов, их результатов и 82 уже написанных моделью символов. Токены
потрачены, данные получены, записи об этом нет нигде, кроме лога клиента.

### Что нужно изменить

- **Пропускать `GraphInterrupt` (и `ParentCommand`).** Там, где обёртка `task` /
  субагента ловит исключения, чтобы превратить их в результат инструмента, эти два
  должны проходить нетронутыми — тогда внешний граф приостановится, а чекпойнтер
  сохранит состояние. Дочернему графу нужен собственный чекпойнтер, иначе
  возобновлять будет нечего.
- **Всегда публиковать терминальное событие.** Ран, который закончился — как бы он
  ни закончился, — обязан отдать ровно одно из `ai.run.completed` / `.error` /
  `.cancelled`. Сейчас повисший `task` не отдаёт ни одного, и замечает это только
  watchdog на клиенте.
- **Сохранять то, что уже произошло.** Ход, отработавший три инструмента и
  написавший текст, не должен исчезать из истории.

**Область:** всё гейтящееся за субагентом — `execute`, `write_file`, `edit_file`,
`deliver_file`, то есть весь путь `code-runner`: файлы, таблицы, исполнение кода.
Инструменты верхнего уровня (`send_email`, `place_call`) в этих снимках не
задействованы и, возможно, работают.

## Часть 2 — как доставленный файл должен попадать в чат?

> **Статус на 2026-09-04, 19:30. Вложение теперь приходит — но без адреса.**
>
> Бек прикрепляет файл к сообщению ассистента, ровно в той форме, которая описана
> ниже, и клиент его мапит и рисует. Не хватает одного, и именно того, что решает
> всё:
>
> ```json
> {"uuid": "81791bd3-98c1-45b8-9d49-0a640524f1ef",
>  "filename": "driver_report_aug_2026.xlsx",
>  "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
>  "file_size": 5455, "status": "ready", "error": null,
>  "file_uuid": null, "download_url": null}
> ```
>
> `status: "ready"`, `error: null`, настоящий `file_size` — файл существует и
> готов. Но **`download_url` пустой и `file_uuid` пустой**, то есть адреса нет
> никакого. Плитка рисуется, пользователь по ней тапает, и открывать нечего. То же
> самое с файлом, который загрузил **пользователь** (`appl-d5.pdf`, 65 237 байт,
> `status: "ready"`, оба поля пустые) — при этом модель его прочитала и
> пересказала, значит байты точно на месте.
>
> Клиент это перекрыть не может: под `/api/v1/ai/` существует только
> `POST /ai/attachments` (загрузка). Ни GET, ни download-url маршрута нет, а
> `GET /core/file-manager/files/{file_uuid}/download-url` требует того самого
> `file_uuid`, который приходит пустым.
>
> **Закрывает вопрос любое из трёх:**
>
> 1. заполнять `download_url` при каждом чтении (переподписывать, а не сохранять
>    один раз — presign протухает, а тред, открытый завтра, должен работать);
> 2. заполнять `file_uuid` — тогда мы сами сходим в существующий
>    `GET /core/file-manager/files/{file_uuid}/download-url`;
> 3. добавить `GET /api/v1/ai/attachments/{uuid}/download-url`.
>
> Вариант (2) вам дешевле всего, если файл и так лежит в файловом менеджере, и
> стоит нам одного небольшого запроса. Вариант (1) — меньше всего работы нам.
> Подходит любой.


Это вопрос, а не баг-репорт. Что должен ожидать клиент после того, как
`deliver_file` отработает, контракт не описывает, и ни одного такого сообщения мы
в трейсах не видели — то есть реализовывать не подо что.

### Что клиент умеет сегодня

| Путь | Статус |
| --- | --- |
| Ссылка в markdown-тексте ответа | **Работает.** Ссылки кликабельны и открываются нативно (`open.url`, только http(s)). |
| Вложение на строке сообщения ассистента | **Отбрасывается.** `AIMessageRead.attachments` мапится только для `role: "user"`; у assistant-строки клиент их выбрасывает и не рисует ничего. |
| Ссылка внутри вьюхи `render_ui` | **Инертна by design.** `<a>` внутри сгенерированных вьюх подменяется обычным текстом — это осознанная граница безопасности, и она не изменится. |
| Открыть presigned-URL нативно | **Работает.** Приложение уже открывает `download_url` для файлов, которые приложил *пользователь*, тем же вызовом моста. |

То есть сегодня работает ровно один путь, и то случайно: обычная ссылка в тексте
ответа.

### Три возможные формы

1. **`attachments` на сообщении ассистента** — тот же `AIAttachmentRead`, что уже
   используется на стороне пользователя: `uuid`, `filename`, `content_type`,
   `file_size`, `download_url`. Эту форму мы бы предпочли: чип рисуется в пузыре,
   переживает перезагрузку, потому что приходит с историей, а у клиента уже есть и
   компонент, и нативное открытие. Не требует ни нового события, ни новой схемы.
2. **Отдельное событие** (`ai.file.delivered` или подобное) с теми же полями плюс
   сохранённая строка, чтобы переоткрытый тред его тоже показывал. Больше
   движущихся частей, а файл, существующий только как событие, исчезает при
   перезагрузке.
3. **Ссылка в тексте** — то, что происходит сейчас случайно. Работает, но файл
   невидим в переписке: ни имени, ни размера, ни иконки, и URL протухает вместе с
   подписью.

### Что нам нужно от вас

- Какая из трёх форм задумана? Если (1) — бек уже прикрепляет доставленный файл к
  строке сообщения ассистента, или `deliver_file` только кладёт его в файловый
  менеджер и упоминает прозой?
- Приходят ли сегодня вложения на сообщениях с ролью `assistant`? Схема это
  позволяет, мы такого не видели ни разу и сейчас их выбрасываем — стоит
  подтвердить до того, как мы построим интерфейс.
- Сколько живёт `download_url` и переподписывается ли он при последующем чтении
  истории? Чип с протухшим URL хуже, чем отсутствие чипа.

### Что мы сделаем, как только получим ответ

Немного, и упирается только в ответ:

1. перестать выбрасывать `attachments` у сообщений ассистента при сборке переписки;
2. отрисовать их существующим компонентом `MessageAttachments` — он уже умеет и
   превью картинок, и плитки файлов;
3. открывать по тапу существующим вызовом моста `attachment.open`.

Отдельно и независимо от этого за нами два своих исправления по флоу согласования
— ни одно из них не является причиной чего-либо из части 1, но оба понадобятся,
как только согласования заработают:

- мы не вызываем `GET /ai/conversations/{uuid}/pending`, поэтому согласование,
  поднятое при закрытом экране чата, вернуть невозможно;
- мы не вызываем `.../release`, поэтому строку, залипшую в `resolving`, нечем
  расклинить.

## Кратко

| Вопрос | Ответ |
| --- | --- |
| Гейт на `deliver_file` — это баг? | Нет, это осознанно и правильно. |
| Почему файл не приходит? | Ран умирает на `execute` — первом гейтящемся вызове внутри субагента, потому что `GraphInterrupt` проглатывается. До `deliver_file` дело не доходит. |
| Есть ли в этом вина клиента? | Нет. Событие, на которое клиент среагировал бы, не публикуется. |
| Может ли клиент показать доставленный файл сегодня? | Только если он придёт ссылкой в тексте ответа. Вложение на сообщении ассистента сейчас отбрасывается. |
| Что блокирует нашу часть? | Знание того, в какой форме бек будет присылать файл. |
