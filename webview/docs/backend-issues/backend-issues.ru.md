# Что не так на беке, если смотреть из мобильного AI-чата

English version: [backend-issues.md](backend-issues.md).

Всё здесь вычитано из сохранённых трейсов диалогов и живых потоков событий
3–4 сентября 2026 на dev-беке, из AI-чата бизнес-приложения. Ничего не выведено
«по поведению» — каждый пункт называет диалог, uuid строк и точный payload,
из которого он взят.

Два пункта блокирующие: система согласований не работает вовсе, а ран может
исчезнуть, унеся с собой весь ход. Остальное — обычные баги плюс две просьбы по
контракту, которые позволили бы клиенту **видеть** сбои, а не догадываться о них.

## 1. Согласование не происходит вовсе — блокер

Пользователь просит отчёт в XLSX, модель делегирует работу субагенту
`code-runner` через `task`, внутри гейтится `execute`, LangGraph поднимает
`GraphInterrupt`, чтобы приостановить граф, — и этот интерапт **ловится и
сериализуется в строку ошибки инструмента** вместо того, чтобы всплыть к
родительскому графу:

```
Tool 'task' failed: GraphInterrupt: (Interrupt(value={'action_requests': [{'name': 'execute',
'args': {'command': 'pwd && ls -la && python3 --version'}, …}],
'review_configs': [{'action_name': 'execute',
'allowed_decisions': ['approve', 'edit', 'reject', 'respond']}]},
id='f56c438ad28bc213d594dc9cadcc09ed'),). Do not retry blindly — …
```

Итого: нет паузы, нет строки `AIPendingAction`, нет события `ai.action.pending`,
одобрять нечего. `GET .../pending` вернул бы пустой список, `resume` нечего
называть. После этого модель говорит пользователю «approve the sandbox run if you
see a pending approval prompt» — про кнопку, которой не может существовать.

`GraphInterrupt` — это управляющий поток LangGraph, а не ошибка. Он обязан дойти
до самого внешнего графа, чтобы чекпойнтер сохранил приостановленное состояние;
обёртка `task` / субагента должна пропускать его (и `ParentCommand`) нетронутым, а
дочернему графу нужен собственный чекпойнтер.

**Область:** всё гейтящееся за субагентом — `execute`, `write_file`, `edit_file`,
`deliver_file`, то есть весь путь `code-runner`: файлы, таблицы, исполнение кода.
Инструменты верхнего уровня (`send_email`, `place_call`) в этих снимках не
задействованы.

Диалог `0a947d85-5334-4491-ba1a-c0e7dca4bc16`, строки
`c47eab02-d528-4288-8e0f-ba59620add8a` и `d0920d87-4bc2-4331-b2ef-ce72f05a0b09`.

## 2. Ран может закончиться без терминального события и потерять весь ход — блокер

Та же просьба, другой день, и на этот раз не вернулось вообще ничего. Ран
`54f8da83-7945-4a53-aee6-3db4e5c5e7da` в диалоге
`d5d653e2-072b-4442-b4a7-369691ecc1d6`:

```
seq 2   ai.tool_call  list_analytics_charts  → результат seq 3   ок
seq 4   ai.tool_call  get_company_overview   → результат seq 5   ок
seq 6   ai.tool_call  run_analytics_chart    → результат seq 7   ок
seq 8-9 ai.token      "I have the driver P&L data … Building the XLSX now."
seq 10  ai.tool_call  task
        … тишина
```

Ни `tool_result`, ни `ai.action.pending`, и **ни одного терминального события** —
ни `ai.run.completed`, ни `.error`, ни `.cancelled`. По контракту стриминга этот
ран до сих пор открыт; клиент выбрался только по собственному 60-секундному
watchdog.

Дальше ход **не сохранился**. Диалог, переоткрытый через минуту, отдаёт 7 строк,
последняя из которых — сообщение самого пользователя:

```
user 20d5bde8 "Gimme in xlsx"   ← последняя строка, дальше пусто
```

Три успешных вызова инструментов, их результаты и 82 уже написанных моделью
символа исчезли. Токены потрачены, данные получены, и никакой записи об этом за
пределами клиентского лога нет.

**Воспроизведено ещё дважды в тот же день**, в том же диалоге, и к этому моменту
картина сжалась до минимума — раны `4d08af72-7de6-46f8-8ad0-7c1eb5825a69` (13:40)
и `c9227f6f-a335-4450-b663-f03bac91db35` (13:42):

```
seq 1-3  ai.token      (29 символов)
seq 4    ai.tool_call  task
         … тишина, дальше наш 60-секундный watchdog
```

Результата инструмента не пришло вообще — даже строки `GraphInterrupt` из §1.
Одного вызова `task` теперь достаточно, чтобы ран повис, и каждая попытка
оставляет на сервере ещё один ран без терминального события.

Нарушены две отдельные гарантии: каждый ран обязан опубликовать ровно одно
терминальное событие, и работа, дошедшая до пользователя, обязана пережить себя в
истории.

## 3. `search_emails` падает на каждом вызове

Три вызова с тремя разными запросами, одно и то же падение:

```
Tool 'search_emails' failed: AttributeError: 'EmailContact' object has no attribute 'get'.
```

Безусловное, а не от данных — что-то обходит объекты `EmailContact` как словари.
Ассистент дважды сказал пользователю, что не может прочитать почту. Диалог
`040934db-884f-4fee-a3f2-96b34a3298ef`, строки `95c920d0-…`, `d286e916-…`,
`59fc88e4-…`.

## 4. Три карточки Metabase отвечают `400 Bad Request`

| Карточка | Ключ чарта | Через что |
| --- | --- | --- |
| 67 | `driver_fuel_usage` | `run_analytics_chart` |
| 66 | `driver_fuel_cost_vs_efficiency` | `run_analytics_chart` |
| 65 | `driver_fuel_cards` | внутри `get_driver_overview` |

Все три — водительские топливные карточки; семь других карточек в том же ходе
приняли ту же форму вызова и вернули данные. Карточка 65 падает **внутри**
успешного инструмента: `get_driver_overview` возвращает `200`, спрятав сбой в поле
`fuel_error` своего тела, что снаружи не видно (см. §8).

## 5. `driver_detail_cards` противоречит двум другим источникам, и это видит пользователь

Один водитель, одно окно в 30 дней, три инструмента, разница в двенадцать раз:

| Источник | Work orders / расходы автопарка |
| --- | --- |
| `driver_detail_cards` | **`work_order_cost: 81469.24`** |
| `driver_fleet_expenses` | 7 ордеров на сумму **`6990`** |
| `get_driver_overview` | `fleet_expense_total: 6990.0`, 7 ордеров |

`net` считается от неверной цифры, поэтому карточка отдаёт
`net: -67127.57886990801` — и ассистент вывел это заголовочной цифрой: «Net P&L:
**-$67,128** — dragged down by $81,469 in work-order costs» — про водителя, у
которого обслуживание за период стоило $6 990.

Первое, что стоит проверить: карточка, похоже, суммирует work orders по всей
компании вместо фильтра по `driver_id`, который `list_analytics_charts` объявляет
для неё обязательным.

## 6. Поиск водителя точный по пробелам

`get_driver_overview {"driver": "Alex Boznikov"}` → `"No driver named 'Alex
Boznikov' in this company."` Водитель существует; `list_available_drivers`
возвращает его как `Alex  Boznikov` — с **двумя пробелами**. Поиск сработал только
когда модель повторила запрос одной фамилией.

Обход стоил затащенного в контекст ответа `list_available_drivers` на 4.7 КБ и
сработал лишь потому, что модель угадала более короткий запрос. Нормализация
пробелов (и регистра) с обеих сторон это чинит.

## 7. `select-branch` не спускался до листа ветки — похоже, исправлено

Описано отдельно в [select-branch-leaf](../select-branch-leaf/select-branch-leaf.ru.md):
возврат к предыдущей версии вопроса отдавал вопрос без ответа под ним, потому что
активный лист парковался на выбранном сообщении, а не на самом глубоком потомке
этой ветки.

Живая спека на dev теперь описывает исправленное поведение («moves the active leaf
to the TIP of that branch … see `message_q.get_deepest_descendant`») — похоже,
починено. Из приложения ещё не перепроверяли, стоит один подтверждающий прогон.

## 8. Контракт: результату инструмента нужен настоящий признак сбоя

Сбои приходят обычным содержимым `ai.tool_result`, поэтому клиент может опознать
их только по английской прозе. Три конкретных следствия:

1. **Форматы разные.** `Tool 'search_emails' failed: …` и
   `Chart 'driver_fuel_usage' failed to run: …` не имеют общего префикса.
   Эвристика, написанная под один, молча пропускает другой — наша так и сделала,
   все три метабейсовых 400 прошли мимо телеметрии.
2. **Сбой внутри успеха не виден.** `get_driver_overview` возвращает `200` с
   `fuel_error` внутри JSON (§4). Снаружи никак не узнать, что трети данных нет.
3. **Пустой результат — не сбой, и отличить нельзя.** «No driver named 'Alex
   Boznikov' in this company.» — законный ответ, и любое строковое правило,
   ловящее два случая выше, рискует поймать и его.

Предлагаем, и в событии, и в сохранённой строке:

```json
{ "tool": "run_analytics_chart", "tool_call_id": "call_…",
  "ok": false,
  "error": { "kind": "upstream_http", "status": 400, "message": "…" },
  "content": "Chart 'driver_fuel_usage' failed to run: …" }
```

`content` пусть остаётся как есть — модель его читает, и это работает. `ok` нужен
всем остальным. Признак `partial` (или `errors: []`) дополнительно закрыл бы
случай 2.

## 9. Контракт: в строках истории нет ничего, что связывает один ход

`AIMessageRead` — это `uuid, role, content, tool_calls, tool_call_id, name,
created_at, attachments, sibling_count`. Ни родителя, ни `run_uuid`, ни
идентификатора хода.

Один ответ хранится несколькими assistant-строками: модель говорит между вызовами
инструментов («сейчас достану чарты», потом вызовы, потом «вот дашборд:», потом
ещё вызовы, потом итог), и каждая реплика — своя строка. Живой стрим показывает
всё это одним пузырём. Поэтому сборка переписки построчно разваливала законченный
ответ на два-три куска, как только тред переоткрывали.

Сейчас мы склеиваем подряд идущие assistant-строки **позиционно** — ход закрывает
только user-строка. Это работает, но это догадка. `run_uuid` (или указатель на
родителя) в строках истории сделал бы склейку точной. `created_at` сейчас
одинаковый у всех строк одного хода — полезная подсказка, но не задокументированная
гарантия.

Важное следствие: `sibling_count` лежит на **первой** строке хода — часто это
пустой анонс вызова инструмента, — поэтому клиент, выбрасывающий пустые строки,
теряет переключатель версий целиком. Мы именно поэтому ключуем склеенный пузырь на
uuid первой строки.

## 11. Группа siblings смешивает роли

`GET /ai/conversations/{uuid}/messages/{message_uuid}/siblings` возвращает группу,
в которой **сообщение пользователя и сообщение ассистента** являются версиями друг
друга. Пять таких групп в одном диалоге
(`d5d653e2-072b-4442-b4a7-369691ecc1d6`, прочитано 2026-09-04 18:18):

```
messageUuid ..fd508fd8  position 1 of 2  roles ["user", "assistant"]  siblings [..fd508fd8, ..87d31f94]
messageUuid ..e8f24eda  position 1 of 2  roles ["user", "assistant"]  siblings [..e8f24eda, ..374bea38]
messageUuid ..51c26238  position 1 of 2  roles ["user", "assistant"]  siblings [..51c26238, ..3ab61870]
messageUuid ..230d8bd4  position 2 of 2  roles ["user", "assistant"]  siblings [..efa94933, ..230d8bd4]
messageUuid ..00215a96  position 2 of 2  roles ["user", "assistant"]  siblings [..1f596bef, ..00215a96]
```

Группа siblings — это «версии одного хода», значит все её члены обязаны иметь одну
роль: варианты вопроса либо варианты ответа. Смешение означает, что переключатель
«1 из 2» под вопросом предлагает заменить его ответом — нажатие подставит на место
пользовательского хода ход ассистента.

В том же диалоге есть и корректная группа (`roles: ["user", "user"]`), то есть это
не общий случай — что-то группирует через границу форка при определённых условиях.

## 12. Мелочи

- `GET /api/v1/ai/models` отвечает
  `{"default": "~deepseek/…", "allowed": [], "options": [{…одна модель…}]}` —
  `allowed` пустой при непустом `options`. Нам не мешает (читаем `options`), но
  между собой они не согласованы.
- Отметки времени одного диалога в двух зонах:
  `created_at: 2026-09-04T14:24:42`, `updated_at: 2026-09-04T14:26:31`, но
  `last_message_at: 2026-09-04T07:26:31` — ровно семь часов разницы, и строки
  сообщений согласуются с `created_at`.

## Как это снято

Веб-чат приложения в отладочной сборке логирует каждый полученный payload
дословно и пробрасывает эти строки в нативный логгер. Каждый пункт выше называет
uuid диалога и uuid строк, так что весь трейс перечитывается через
`GET /ai/conversations/{uuid}/messages/history`.

Упомянутые диалоги: `0a947d85-5334-4491-ba1a-c0e7dca4bc16`,
`d5d653e2-072b-4442-b4a7-369691ecc1d6`, `040934db-884f-4fee-a3f2-96b34a3298ef`,
`1772bfae-939d-45e9-b70e-86e553421d96`, `0515640a-00ba-44eb-b770-4ef567d84943`.
