# Вложения приходят без адреса: `download_url` и `file_uuid` оба пустые

English version: [attachment-no-url.md](attachment-no-url.md).

**Одной строкой:** `GET /ai/conversations/{uuid}/messages/history` возвращает
вложения со `status: "ready"`, настоящим `file_size` и **без единого способа
получить байты** — и `download_url`, и `file_uuid` приходят `null`. Приложение
рисует файл, пользователь по нему тапает, и открывать нечего.

Это касается **обоих направлений**: и файлов, которые доставляет ассистент, и
файлов, которые загрузил пользователь. Загрузка работает, модель файл читает,
строка сохраняется правильно — не хватает только адреса для клиента.

---

## Доказательства

Снято 2026-09-04, 19:26–19:30 на dev, прочитано обратно в 19:34.

Сообщение ассистента `a8088fc8-d7f7-47f1-983a-f0db3a483beb`, `created_at
2026-09-04T19:26:25`:

### Что клиент пишет в лог при тапе

```

  {"name": "appl-d5.pdf", "id": "04c8ba51-…", "status": "ready", "error": null,
   "contentType": "application/pdf"}
```

Шесть тапов по PDF, три по XLSX — все одинаковые.

## Почему клиент не может это обойти

Маршрута к сохранённому AI-вложению не существует. Под `/api/v1/ai/` в
опубликованной спеке есть ровно один эндпоинт для вложений:

```
POST /api/v1/ai/attachments      ← загрузка
```

Ни `GET`, ни download-url. У файлового менеджера такой маршрут есть —
`GET /api/v1/core/file-manager/files/{file_uuid}/download-url`, — но ему нужен тот
самый `file_uuid`, который приходит `null`.

То есть у клиента на руках имя файла, размер, MIME и слово «ready» — и никакого
адреса. Из uuid, который API нигде не принимает, ничего собрать нельзя.

---

## Что видит пользователь

Плитка рисуется правильно — имя, размер, иконка, — а тап теперь говорит «This file
isn't available yet.» Это честное прочтение `download_url: null`, но по сути
неверное: файл **готов**, просто получить его невозможно. До появления этого
сообщения тап вообще ничего не делал.

Ассистент, который собрал отчёт и не смог его отдать, хуже того, который бы его не
предлагал: работа сделана, токены потрачены, результат недостижим.

## Три способа закрыть — достаточно любого

1. **Заполнять `download_url` при каждом чтении.** Переподписывать на каждый
   запрос, а не сохранять одну ссылку: presign протухает (судя по `Expires=` в
   S3-ссылках, которые модель вставляет в ответы, у вас это около часа), а тред,
   открытый завтра, обязан работать.
2. **Заполнять `file_uuid`.** Если файл и так лежит в файловом менеджере, это
   самая дешёвая правка на вашей стороне, а адрес мы получим сами через
   существующий `GET /core/file-manager/files/{file_uuid}/download-url`.
3. **Добавить `GET /api/v1/ai/attachments/{uuid}/download-url`.** Самый явный
   вариант и единственный, который с точки зрения клиента не протухает.

Мы предпочли бы (1) или (2): (1) — меньше всего работы нам, (2) — вероятно, вам.
Скажите, какой выбираете: правка на клиенте в каждом случае разная, но небольшая.

---

## Как проверить, что починилось

1. Загрузите любой файл в чат или попросите отчёт в `.xlsx`.
2. Выйдите из чата и зайдите заново — это заставит прочитать историю, а не
   локальную оптимистичную копию.
3. `GET /ai/conversations/{uuid}/messages/history` должен вернуть это вложение с
   рабочим `download_url` (или с непустым `file_uuid`).
4. Тап по плитке в приложении должен открыть файл.

Шаг 2 принципиален: сразу после загрузки приложение показывает собственное
локальное превью, поэтому баг не виден, пока тред не переоткроют.

---

## Заодно, раз уж вы там

- `status: "ready"` без адреса противоречит сам себе. Если файл может быть
  сохранён, но не выдан, у этого состояния должно быть своё значение `status` и
  свой `error` — тогда клиент сможет сказать о нём правду.
- В том же ответе `modality: "text"` у PDF и `null` у XLSX. Не блокирует, но смысл
  поля снаружи неочевиден.
