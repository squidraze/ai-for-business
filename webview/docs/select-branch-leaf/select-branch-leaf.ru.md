# `select-branch` возвращает ветку без ответа на ней

English version: [select-branch-leaf.md](select-branch-leaf.md).

> **Статус на 2026-09-04.** Живая спека на dev теперь описывает ровно то
> поведение, которого просит этот отчёт: «pointing at a message that already has a
> reply under it moves the active leaf to the **TIP** of that branch (the deepest
> descendant … see `message_q.get_deepest_descendant`), not the target itself».
> В нашем запиненном снапшоте OpenAPI всё ещё старая формулировка — значит правка
> приехала после снятого ниже снимка. **Из приложения ещё не перепроверено** —
> отчёт оставлен как запись наблюдённого и как сценарий для повторного прогона.

**Одной строкой:** после `POST /messages/{uuid}/select-branch` следующий
`GET /messages/history` возвращает выбранное сообщение и **ничего под ним** —
ответ, сгенерированный на этой ветке, не попадает в путь и недоступен даже при
явной адресации через `?leaf=`. Для пользователя это выглядит так: возврат к
предыдущей версии вопроса удаляет ответ, который там был.

Остальное в ветвлении работает верно (см. [Что уже работает](#что-уже-работает)) —
отчёт про один шаг.

---

## Окружение

| | |
| --- | --- |
| Бек | dev (`api` за мобильным приложением), 2026-09-03, ~17:08 по времени устройства |
| Клиент | business app (Android), веб-чат в WebView, пользователь `139` |
| Диалог | `0515640a-00ba-44eb-b770-4ef567d84943` |
| Повторено на | `1772bfae-939d-45e9-b70e-86e553421d96`, в тот же день ~16:58 |

Оба диалога лежат в dev-базе и никуда не делись — прямой запрос к любому из них
закрывает вопрос, поставленный в конце файла.

## Воспроизведение

1. **Новый диалог, вопрос A.**
   `POST /api/v1/ai/messages` → пользовательское сообщение
   `bb09c778-5396-4982-8546-4d4bf68c5a60` (56 символов). Ран завершается, ответ
   ассистента генерируется и доезжает до клиента стримом.

2. **Редактируем вопрос A** — форк.
   `POST /api/v1/ai/conversations/0515640a-…/messages/bb09c778-…/edit` → `202`.
   Новый пользовательский sibling `90050d01-f84f-4ced-852c-22a88150d409`
   (74 символа), ран `66a3a749-d9cb-4db7-85c8-c7392626681f`, ответ `…ff04df7c` на
   1276 символов.

3. **История после форка — верно.**
   `GET /messages/history?limit=100` → 2 строки:

   ```
   user       90050d01-…8150d409   74ch    sibling_count: 2
   assistant  …ff04df7c          1276ch
   ```

4. **Siblings — верно.**
   `GET /messages/90050d01-…/siblings` →
   `[bb09c778-…, 90050d01-…]`, обе `role: "user"`, отредактированная на позиции 2.

5. **Переключаемся обратно на версию 1.**
   `POST /messages/bb09c778-…/select-branch` → `200`

   ```json
   { "conversation_uuid": "0515640a-…", "active_leaf_message_uuid": "bb09c778-5396-4982-8546-4d4bf68c5a60" }
   ```

   Активный лист вернулся **тем же сообщением, которое передали**.

6. **История на ставшей активной ветке — баг.**
   `GET /messages/history?limit=100` → **1 строка**:

   ```
   user  bb09c778-…f68c5a60  56ch  sibling_count: 2
   ```

   Ответа, сгенерированного на шаге 1, нет. Ни одной assistant-строки — ни
   пустой, ни какой-либо ещё.

7. **Та же ветка с явной адресацией — тоже пусто.**
   `GET /messages/history?leaf=bb09c778-…&limit=100` → **1 строка**, идентично
   шагу 6.

---

## Чего мы ожидали

`select-branch` по сообщению, у которого есть потомки, должен делать активной
**всю ветку**: активным листом должно становиться самое глубокое сообщение,
достижимое от выбранного по цепочке активных детей, а не само выбранное
сообщение. Тогда шаг 6 вернул бы:

```
user       bb09c778-…   56ch
assistant  <ответ на A>
```

Сейчас `active_leaf_message_uuid` возвращается без изменений, а `history` отдаёт
путь **до** листа — поэтому ветка, выбранная по *пользовательскому* сообщению,
принципиально не может содержать свой ответ: ответ является потомком листа, а
потомки в путь не входят.

---

## Почему это нельзя обойти на клиенте

Очевидный обход — перечитать ветку, адресуя её последним сообщением. Такой
возможности нет:

- `history?leaf=X` возвращает предков `X` (подтверждено на шаге 7: передали
  пользовательское сообщение — получили только его);
- другого uuid у клиента нет. `siblings` по пользовательскому сообщению отдаёт
  только пользовательские сообщения, а ответ, живущий под архивной версией, этому
  клиенту никогда не присылали — его uuid здесь неизвестен.

То есть сегодня нет запроса, которым приложение могло бы получить «ветку под
`bb09c778`». Поэтому это заведено на бек, а не обойдено у нас.

---

## Влияние

Весь смысл ветвления в том, что форк **никогда не разрушает** предыдущую версию —
именно это делает «перегенерировать» и «отредактировать» безопасными действиями.
Сейчас возврат к предыдущей версии показывает вопрос и пустоту на месте ответа,
что читается ровно как потеря данных. Пользователи описывают это как «ответ ИИ
пропал».

---

## Две гипотезы — подтвердите, какая

1. **Указатель активного листа не спускается вниз** (на это указывают данные).
   `select-branch` пишет `active_leaf = <переданное сообщение>` вместо того, чтобы
   спуститься по ветке до последнего сообщения. Правка — в `select-branch`.

2. **Ответ на A был переподвешен или отвязан при форке.** Если `edit` перенёс
   существующий ответ на нового sibling'а или отвязал его, никакая правка
   указателя не поможет — вопрос к модели данных.

Прямой запрос по диалогу `0515640a-00ba-44eb-b770-4ef567d84943` — «какие строки
имеют `parent = bb09c778-5396-4982-8546-4d4bf68c5a60`» — разделяет эти два
случая сразу.

### Вопросы

- Спускается ли `select-branch` до самого глубокого потомка выбранного сообщения
  или сохраняет переданный uuid как активный лист?
- `history?leaf=X` определён как «путь, оканчивающийся на `X`» (только предки)?
  Если да — есть ли способ запросить ветку **под** сообщением?
- После того как `edit` форкает пользовательский ход, сохраняет ли исходный ход
  свой ответ как ребёнка?

## Что уже работает

Перечислено, чтобы это не задело правкой:

- `POST .../edit` — форкает пользовательского sibling'а, сразу отдаёт реальный
  `message_uuid`, последующий ран корректно порождает ответ.
- `GET .../messages/history` — свёрнутый трейс и `sibling_count` верны на ветке,
  которая действительно активна (шаг 3).
- `GET .../messages/{uuid}/siblings` — отдаёт обе версии, от старой к новой, с
  верными ролями и порядком (шаг 4).
- `POST .../select-branch` — отвечает `200`, само переключение происходит; неверен
  только лист, на который оно приземляется.
