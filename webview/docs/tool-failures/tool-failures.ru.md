English version: [tool-failures.md](tool-failures.md).

Все четыре вычитаны из сохранённого трейса одного диалога 2026-09-04. Ни один из
них не ломает ассистента — агент каждый раз выкручивается и объясняет ситуацию
пользователю словами, — и именно поэтому в обычной работе они невидимы и стоят
того, чтобы их записать.

Последний раздел — не баг, а просьба по контракту: сегодня провалившийся
инструмент отличается от успешного только английской прозой в теле ответа, а один

## 3. `driver_detail_cards` противоречит двум другим источникам

Три инструмента в одном ходе спросили про одного водителя и одно окно в 30 дней
(`2026-08-06` → `2026-09-04`). Расхождение — в двенадцать раз:

| Источник | Work orders / расходы автопарка | Строка |
| --- | --- | --- |
| `driver_detail_cards` | **`work_order_cost: 81469.24`** | `62244c6a-d2a4-4850-9932-47590ab74ca2` |
| `driver_fleet_expenses` | 7 ордеров на сумму **`6990`** | `49facafd-06f0-479c-8631-1c0f5c66ad66` |
| `get_driver_overview` | `fleet_expense_total: 6990.0`, `fleet_expense_work_orders: 7` | `7ac7317b-2f61-46f1-8891-c6a758e0250e` |

Два источника из трёх совпадают точно. Третий даёт 81 469.24, и, так как `net`
считается от него, `driver_detail_cards` возвращает:

```json
{"trips": 16, "total_revenue": 26466.0, "driver_earnings": 9560.44,
 "work_order_cost": 81469.24, "net": -67127.57886990801}
```

**Это дошло до пользователя.** Ассистент вывел цифру в карточке статистики и
написал: «Net P&L: **-$67,128** — dragged down by $81,469 in work-order
(maintenance) costs» — про водителя, у которого обслуживание за период стоило
$6 990.

Постатейный список из `driver_fleet_expenses` — это весь период: WO-3102 $1 240,
WO-3101 $860, WO-001 $0, WO-3103 $0, WO-OWN-001 $1 850, WO-OWN-003 $2 400,
WO-OWN-002 $640 — ровно $6 990, что совпадает с `get_driver_overview`.

Наша догадка, которую стоит проверить первой: `driver_detail_cards` суммирует
work orders **по всей компании**, а не фильтрует по `driver_id`, хотя `driver_id`
объявлен для неё обязательным в `list_analytics_charts`.

## 4. `get_driver_overview` не находит водителя с двойным пробелом в имени

```
call_6c07f6b8a1f8421bb4f9050f  get_driver_overview {"driver": "Alex Boznikov", "period": "last_30_days"}
  → "No driver named 'Alex Boznikov' in this company."          (строка a5709e41-5c2f-420f-90ae-16a57b0e7946)
```

Водитель существует. `list_available_drivers`, вызванный сразу следом, возвращает
его как:

```
- Alex  Boznikov — status: covered — (255) 588-8899 (id: 2e64eb09-4924-4503-a7d8-e873d1e35547)
```

— с **двумя пробелами** между именем и фамилией. Поиск сработал только когда
модель повторила запрос одной фамилией (`{"driver": "Boznikov"}`, строка
`7ac7317b-…`).

То есть сравнение имени точное, без нормализации пробелов. Цена этого — не только
неудачный вызов: чтобы выкрутиться, агент затащил в контекст весь список
водителей, 4.7 КБ результата, и получилось это лишь потому, что модель угадала
более короткий запрос. Пользователь, спросивший про любого водителя, у которого в
записи затесался лишний пробел, получит «такого водителя нет».

Нормализация пробелов (и регистра) с обеих сторон сравнения это чинит.

## 5. Согласование не происходит вовсе: `GraphInterrupt` проглатывается внутри `task`

Самый серьёзный из пяти: **флоу согласования (HITL) не работает вообще ни для чего,
что идёт через субагента.** Нет паузы, нет строки pending, нет события, одобрять
нечего.

Диалог `0a947d85-5334-4491-ba1a-c0e7dca4bc16`, две попытки с разницей в двадцать
минут, обе одинаковые. Сохранённый результат инструмента:

```
Tool 'task' failed: GraphInterrupt: (Interrupt(value={'action_requests': [{'name': 'execute',
'args': {'command': 'pwd && ls -la && python3 --version'},
'description': "Tool execution requires approval\n\nTool: execute\nArgs: {'command': '…'}"}],
'review_configs': [{'action_name': 'execute',
'allowed_decisions': ['approve', 'edit', 'reject', 'respond']}]},
id='f56c438ad28bc213d594dc9cadcc09ed'),). Do not retry blindly — consider whether you
can answer without it.
```

| Попытка | Вызов `task` | Строка результата | id интерапта |
| --- | --- | --- | --- |
| 1 (13:51) | `call_7525f60a386547c2a1da245a` | `c47eab02-d528-4288-8e0f-ba59620add8a` | `f56c438ad28bc213d594dc9cadcc09ed` |
| 2 (14:11) | `call_cde0a645518149f8ba6280a9` | `d0920d87-4bc2-4331-b2ef-ce72f05a0b09` | `febfea52014c24630cf2806c6068edba` |

Пользователь попросил отчёт в XLSX. Модель делегировала работу субагенту
`code-runner` через `task`; внутри `execute` гейтится, LangGraph поднял
`GraphInterrupt`, чтобы приостановить граф, — и этот интерапт был **пойман и
сериализован в строку ошибки инструмента** вместо того, чтобы всплыть к
родительскому графу.

Дальше по цепочке:

1. ран не встаёт на паузу, значит строка `AIPendingAction` не создаётся;
2. событие `ai.action.pending` не публикуется — это можно утверждать
   положительно: наш клиент логирует его по имени
   (`ai.action.pending — run paused for human approval`), и в снимке, где есть обе
   попытки, его нет нигде;
3. следовательно, одобрять нечего: `GET .../pending` вернул бы пустой список, а
   `resume` нечего называть в `pending_uuid`;
4. модель читает текст ошибки и говорит пользователю «the run keeps getting
   interrupted before it can execute… approve the sandbox run if you see a pending
   approval prompt» — то есть просит нажать кнопку, которой не может существовать.

`GraphInterrupt` — это **управляющий поток LangGraph, а не ошибка**: он обязан
дойти до самого внешнего графа, чтобы чекпойнтер сохранил приостановленное
состояние. Там, где обёртка `task` / субагента ловит исключения, чтобы превратить
их в результат инструмента, `GraphInterrupt` (и `ParentCommand`) нужно пропускать
нетронутыми — а дочернему графу нужен собственный чекпойнтер, иначе возобновлять
будет нечего.

### У того же бага есть вторая, более тяжёлая форма: ран замолкает

Диалог `d5d653e2-072b-4442-b4a7-369691ecc1d6`, ран
`54f8da83-7945-4a53-aee6-3db4e5c5e7da`, 2026-09-04, 14:26 серверного времени. Та же
просьба (отчёт в XLSX), та же делегация в `code-runner`, и на этот раз не пришло
вообще ничего:

```
seq 2   ai.tool_call    list_analytics_charts      → ai.tool_result seq 3   ok
seq 4   ai.tool_call    get_company_overview       → ai.tool_result seq 5   ok
seq 6   ai.tool_call    run_analytics_chart        → ai.tool_result seq 7   ok
seq 8-9 ai.token        "I have the driver P&L data for last month (Aug 1–31, 2026).
                         Building the XLSX now."
seq 10  ai.tool_call    task
        …и тишина. Ни tool_result, ни ai.action.pending, ни терминального события.
```

Через шестьдесят секунд наш собственный watchdog закрыл стрим на клиенте. Ран не
опубликовал **ни одного терминального события** — ни `ai.run.completed`, ни
`ai.run.error`, ни `ai.run.cancelled`, — то есть по контракту он до сих пор открыт.

Хуже того, **ничего не сохранилось**. Диалог, переоткрытый через минуту, отдаёт 7
строк, последняя из которых — сообщение самого пользователя:

```
user      05eada71  "Gimme me report xlsx"
assistant 85a1d41e  "What report would you like? …"
user      99973789  "Driver report"
assistant f66540af  (tool_calls: list_available_drivers)
tool      67c60e76  tool_result:list_available_drivers
assistant 272198a8  "Which driver would you like the report for? …"
user      20d5bde8  "Gimme in xlsx"        ← последняя строка, дальше пусто
```

Три успешных вызова инструментов, их результаты и 82 символа, которые модель уже
написала, исчезли. Вопрос пользователя висит без ответа, и единственная запись о
том, что вообще что-то происходило, — лог клиента.

Воспроизведено ещё дважды в тот же день и в том же диалоге — раны
`4d08af72-7de6-46f8-8ad0-7c1eb5825a69` (13:40) и
`c9227f6f-a335-4450-b663-f03bac91db35` (13:42), — и к этому моменту всё свелось к
`ai.token` на 29 символов, одному `ai.tool_call task` на seq 4 и тишине. Результата
инструмента не пришло вообще, даже строки `GraphInterrupt`. Одного вызова `task`
достаточно.

То есть один и тот же путь `task`/`GraphInterrupt` ломается двумя способами:
иногда интерапт возвращается строкой ошибки инструмента (выше), иногда ран просто
перестаёт публиковать и не оставляет следа. Обоим нужно, чтобы интерапт доходил до
родительского графа; второй случай вдобавок означает, что ран может закончиться
без терминального события, чего по контракту стриминга быть не может.

**Область.** Всё гейтящееся, что живёт за субагентом: `execute`, `write_file`,
`edit_file`, `deliver_file` — то есть весь путь `code-runner`: файлы, таблицы,
исполнение кода. Про инструменты верхнего уровня (`send_email`, `place_call`) этот
снимок ничего не говорит — возможно, они паузят корректно; такая же проверка
займёт минуту.

**Клиент тут ничем помочь не может.** Мы не пропускаем событие — событие не
отправляется. (Отдельно: мы пока не вызываем `GET .../pending` — это наш
собственный пробел для согласований, поднятых при закрытом экране; к этому случаю
он отношения не имеет и не помог бы.)

## Просьба по контракту: настоящий признак сбоя в результате инструмента

Всё описанное выше клиент сегодня может обнаружить только чтением английской
прозы: инструменты возвращают сбой обычным содержимым `ai.tool_result`, и в вашей
же документации это записано как известный пробел. Три конкретных следствия, на
которые мы наткнулись:

1. **Форматы разные.** `Tool 'search_emails' failed: …` и
   `Chart 'driver_fuel_usage' failed to run: …` не имеют общего префикса, поэтому
   клиентская эвристика, написанная под один, молча пропускает другой. Наша так и
   сделала: все три метабейсовых 400 прошли мимо телеметрии.
2. **Сбой внутри успеха не виден.** `get_driver_overview` выше вернул `200`, а
   `fuel_error` лежал внутри JSON. Снаружи никак не узнать, что трети данных нет.
3. **Пустой результат — не сбой, а отличить нельзя.**
   `"No driver named 'Alex Boznikov' in this company."` — совершенно нормальный
   ответ (здесь он ошибочен по причине из §4, но это не ошибка инструмента). Любое
   правило по подстроке, ловящее §1 и §2, рискует поймать и это.

Что закрыло бы вопрос — признак рядом с содержимым, и в событии `ai.tool_result`,
и в сохранённой tool-строке:

```json
{
  "event_type": "ai.tool_result",
  "data": {
    "tool": "run_analytics_chart",
    "tool_call_id": "call_…",
    "ok": false,
    "error": { "kind": "upstream_http", "status": 400, "message": "…" },
    "content": "Chart 'driver_fuel_usage' failed to run: …"
  }
}
```

`content` может остаться ровно таким, какой есть — модель его читает, и это
работает. `ok` нужен всем остальным. Признак `partial` (или список `errors: []`)
дополнительно закрыл бы случай 2, где вызов удался, а часть данных нет.

### Что клиент делает со сбоями сегодня

Контекст, чтобы просьба не читалась как заявка на новый интерфейс:

- **Пользователю не показывается ничего.** Сбой инструмента это не сбой рана, а
  агент и так объясняется словами — лучше, чем это сделал бы баннер. Ошибку мы
  показываем только когда ран завершился, не произведя вообще ничего.
- **Сырое содержимое инструмента на экран не попадает.** Это контекст для модели,
  мы его отбрасываем при сборке переписки.
- **Мы это логируем — ради чего флаг и нужен.** Мы единственные, кто видит эти
  результаты в обычной работе и может сказать «у этого пользователя сегодня два
  чарта из девяти не открылись».

## Мелочи из того же снимка

- `GET /api/v1/ai/models` отвечает
  `{"default": "~deepseek/deepseek-v4-flash-latest", "allowed": [], "options": [{…одна модель…}]}`
  — `allowed` пустой при непустом `options`. Нам не мешает (мы читаем `options`),
  но между собой они не согласованы.
- Отметки времени одного диалога в разных зонах:
  `created_at: 2026-09-04T13:20:50`, `updated_at: 2026-09-04T13:50:01`, но
  `last_message_at: 2026-09-04T06:50:38` — ровно семь часов разницы. Строки
  сообщений согласуются с `created_at`, а не с `last_message_at`.
