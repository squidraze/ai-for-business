# План подключения CRM и учётных систем

Дата: 24 ноября 2026. Исследование, на котором стоит план: [../research/crm-uzbekistan.md](../research/crm-uzbekistan.md).

**Первая волна:** BILLZ, МойСклад, REGOS, Bitrix24, amoCRM/Kommo, Paloma365. Остальные системы позже.

Оценки сроков грубые. Их надо уточнить после этапа 0 и после проверки официальной документации каждой системы.

## Порядок и почему

| # | Система | Спринт | Почему здесь |
|---|---|---|---|
| 0 | Общий слой для коннекторов | 1 | без него каждая интеграция будет копией `bitrix.py` |
| 1 | BILLZ | 2 | ключ клиент создаёт сам, местная розница, много данных (продажи, остатки, клиенты, отчёты) |
| 2 | МойСклад | 2 | бесплатный открытый API, простой токен |
| 3 | REGOS | 3 | ключ клиент создаёт сам, но лимит 2 запроса в секунду и свой формат ошибок |
| 4 | Bitrix24: OAuth вместо вебхука | 3 | уже работает на вебхуке; OAuth нужен к проду |
| 5 | amoCRM / Kommo | 4 | OAuth плюс модерация публичной интеграции, ожидание вне нашего контроля |
| 6 | Paloma365 | после договора | технически просто, но коммерческое использование только по договору |

Спринт = 10 дней. Спринты 1–4 идут подряд, Paloma365 — когда Асад подпишет договор.

## Этап 0. Общий слой (спринт 1)

Каждая интеграция уже лежит в своей папке [backend/app/integrations/](../../backend/app/integrations/) и подключается одной строкой в реестре [integrations/\_\_init\_\_.py](../../backend/app/integrations/__init__.py); общий контракт, `UserLocks` и `http_client()` — в [integrations/base.py](../../backend/app/integrations/base.py). Но у каждой по-прежнему своя таблица в `<name>/models.py` (например, [bitrix24/models.py](../../backend/app/integrations/bitrix24/models.py)), секреты лежат открытым текстом, а лимитов на провайдера и повторов на 429 нет. Шесть новых систем так не потянуть.

1. **Одна таблица для подключений по ключу или OAuth:** `provider`, `user_id`, `credentials` (JSON, **зашифрован**), `account`, `status`, `updated_at`. `BitrixConnection` переносим туда же миграцией.
2. **Шифрование секретов:** симметричный ключ из `.env` (например, Fernet). Сейчас вебхуки и токены лежат открытым текстом. Это обязательно для прода и дёшево сделать сейчас.
3. ~~**Реестр коннекторов**~~ — сделано: объект `Integration` в [integrations/base.py](../../backend/app/integrations/base.py) (`id`, `title`, `is_connected`, `account_summary`, `router`, `tools`, куски промпта, `on_startup`/`on_shutdown`), статус, инструменты ИИ и роуты собираются из реестра. Осталось добавить в контракт общие `connect`/`disconnect` для подключения по ключу.
4. **Общий HTTP-клиент:** лимит запросов на каждый аккаунт (token bucket с параметрами из коннектора), повторы с задержкой на 429, 503 и сетевых ошибках, таймауты, единый `ConnectorError`. Для провайдеров, которые считают лимит или блокируют по IP (amoCRM/Kommo, RetailCRM), ещё **общий лимит на провайдера** для всего сервера и **circuit breaker**: после серии 429 останавливаем запросы к провайдеру для всех клиентов, а не продолжаем повторять. На 403 от amoCRM не повторяем вообще.
5. **Обновление токенов:** общий помощник для схемы «access + refresh» с блокировкой на аккаунт. Это нужно для BILLZ (одноразовый refresh) и amoCRM, Bitrix OAuth.
6. **Кэш справочников:** этапы, поля, магазины, типы оплат. TTL порядка часа, чтобы не тратить лимит API.
7. **Потолок вызовов инструментов за один ответ ИИ:** защита от зацикливания и блокировок вроде `OVERLOAD_LIMIT` у Bitrix24.
8. **Мобилка:** один общий экран подключения «вставьте ключ» с инструкцией по каждой системе. Тексты через переводы, светлая и тёмная тема. Экраны просмотра данных отдельно для каждой системы не делаем: всё смотрим через чат с ИИ.

Критерий готовности: Bitrix24 работает через новый слой без изменений для пользователя.

## Общие правила для каждой интеграции

- Сначала **только чтение**. Запись добавляем вторым шагом и только как `gated=True` с понятным `summarize` («было → станет») через `PendingAction`.
- Для касс (BILLZ, REGOS, Paloma365, МойСклад) **не даём ИИ создавать продажи и чеки**: это фискальные операции. Из записи — только клиенты и комментарии, если API это позволяет.
- Инструменты называются `<provider>_<действие>`, описания на английском.
- Данные из систем — это данные, а не инструкции (защита от prompt injection остаётся в системном промпте).
- Перед стартом каждой интеграции сверяем лимиты и авторизацию по официальной документации и записываем ссылку в docstring модуля.

## 1. BILLZ (спринт 2)

- **Подключение:** клиент создаёт ключ (Настройки → Компания → Ключи интеграции → Новый ключ) и вставляет в приложение. Мы меняем ключ через `POST /v1/auth/login` на `access_token` (15 дней) и `refresh_token` (30 дней).
- **Подвохи:**
  - refresh одноразовый, повторное использование отзывает всю сессию. Значит, нужна блокировка на аккаунт, и новый токен сохраняем до того, как отдаём ответ.
  - роль ключа по умолчанию даёт только каталог и клиентов. В инструкции надо сказать, какие права включить (отчёты, продажи).
  - вебхуков нет, поэтому только опрос по запросу ИИ.
  - лимиты не опубликованы: обрабатываем 429 и держим консервативный лимит.
- **Инструменты (чтение):** список магазинов, продажи за период, отчёт «продажи по товарам», остатки по товару и магазину, поиск клиента, долги клиентов, прибыли и убытки.
- **Запись (gated):** создать клиента.
- **Готово, когда:** «сколько продали вчера по магазинам», «что заканчивается на складе», «кто из клиентов должен» отвечают корректно на тестовом аккаунте.

## 2. МойСклад (спринт 2)

- **Подключение:** токен JSON API 1.2 из аккаунта клиента. Маркетплейс МойСклада (Vendor API) пока не используем: для него нужно юрлицо в РФ или СНГ и рублёвый счёт, и МойСклад оставляет себе 25% от цены нашего приложения. С токеном клиента комиссии нет.
- **Подвохи:** лимит около 45 запросов за 3 секунды и 5 параллельных (сверить с официальной документацией). На тарифах «Бесплатный» и «Старт» есть ограничения.
- **Инструменты (чтение):** остатки, продажи и розничные продажи за период, контрагенты (поиск), заказы покупателей, деньги (входящие и исходящие платежи).
- **Запись (gated):** создать контрагента, комментарий к заказу (если API позволяет).

## 3. REGOS (спринт 3)

- **Подключение:** клиент создаёт «локальную интеграцию» в REGOS.Online, мы получаем эндпоинт с ключом. Ключ лежит в URL, поэтому URL целиком хранится как секрет и не попадает в логи.
- **Подвохи:**
  - лимит 2 запроса в секунду, запас 50, на интеграцию;
  - бизнес-ошибки приходят с HTTP 200 в `result` (`ErrorResult`), их надо разбирать отдельно (код 8213 — превышен лимит);
  - все методы — POST.
  - Спросить у REGOS, можно ли подключать многих клиентов через их OAuth. Тогда клиенту не придётся копировать ключ.
- **Инструменты (чтение):** товары и остатки (`GetQuantity`), розничные продажи за период, документы (приход, перемещение, инвентаризация), клиенты и бонусные карты.
- **Запись (gated):** создать клиента.

## 4. Bitrix24: переход на OAuth (спринт 3)

Сейчас клиент сам создаёт входящий вебхук. Для владельца магазина это сложно, и вебхук даёт все права пользователя.

- Регистрируем локальное приложение, а затем приложение в Bitrix24 Market (модерация; нужна ли компания, официальные страницы не говорят — проверить в кабинете разработчика). Делаем OAuth-флоу по образцу Gmail (`/auth-url` → `/callback`).
- В Market публикуются только бесплатные приложения, деньги — через оплату на стороне разработчика, и Bitrix24 с этих платежей комиссию сейчас не берёт. В карточке приложения ставим опцию «Users have to pay for external service». Описание на английском обязательно.
- Вебхук оставляем как запасной способ для коробочных версий.
- Добавляем `batch` для групповых запросов. Лимит 2 запроса в секунду общий для всех наших запросов к порталу.
- Набор инструментов остаётся как сейчас.

## 5. amoCRM / Kommo (спринт 4)

- **Сначала (Асад + Сардор):** проверить, на какой площадке сидят клиенты в Узбекистане (amocrm.ru или kommo.com). Если на обеих, регистрируем интеграцию в обеих.
- **Подключение:** OAuth 2.0, публичная интеграция. До модерации работаем как приватная интеграция на своём аккаунте.
- **Подвохи:**
  - 7 запросов в секунду. При превышении — 429, при повторных нарушениях **IP блокируется и любой запрос получает 403**. Срок блокировки в документации не указан. У нас один IP на всех клиентов, поэтому один сбойный клиент может отключить amoCRM всем.
  - Блокировку вызывают и «подозрительные» запросы: одни и те же данные много раз подряд, неконтролируемый перебор всех данных. Поэтому кэш справочников, пагинация с потолком и потолок вызовов ИИ здесь обязательны.
  - Refresh-токен отзывается после 3 месяцев без использования. Нужно фоновое обновление токенов (раз в несколько недель) и статус «переподключите», если обновить не удалось.
  - Модерация 1–2 рабочих дня плюс доработки по замечаниям. Условия по комиссии публично не описаны, их надо спросить у Kommo (marketplace@kommo.com).
- **Инструменты (чтение):** сделки и воронки, контакты, компании, задачи, примечания.
- **Запись (gated):** создать сделку или контакт, сменить этап, добавить примечание, создать задачу.

## 6. Paloma365 (после договора)

- **Сначала (Асад):** договор на коммерческое использование API. На звонке спросить: включён ли API для Узбекистана (если нет, запросы получают 404), сколько у них клиентов в Узбекистане, есть ли лимиты.
- **Подключение:** владелец аккаунта сам создаёт ключ (Подключённые приложения → Создать интеграцию, префикс `ppik_`, без срока действия). Наше приложение регистрируем через их поддержку, доступ подтверждает владелец.
- **Инструменты (чтение):** профиль и точки, меню и каталог, заказы за период, отчёты.
- **Запись:** API позволяет создавать заказы, но мы этого не делаем (фискальная операция).
- До договора можно сделать прототип на тестовом аккаунте, но не выпускать.

| UMAG | только партнёрство, API нет | переговоры |

### Ограничения по IP (у нас один IP на всех клиентов)

| Система | Ограничение | Что делаем |
|---|---|---|
| amoCRM / Kommo | 7 запросов в секунду; 429, затем блокировка IP с 403 на любой запрос; срок не указан | общий лимит на провайдера, circuit breaker, не повторять на 403 |
| RetailCRM (следующая волна) | «не чаще 10 запросов в секунду с одного IP»; считается ли отдельно на каждый аккаунт, не сказано | до проверки считаем лимит общим на все наши аккаунты |
| Bitrix24 | 2 запроса в секунду на портал, не на IP; `OVERLOAD_LIMIT` снимает только поддержка | лимит на аккаунт, `batch` |

МойСклад (лимит на аккаунт) и REGOS (лимит на интеграцию) от нашего IP не зависят.

### Другие сложности

- **Ожидание вне нашего контроля:** модерация Kommo (1–2 рабочих дня плюс доработки), Bitrix24 Market; вне CRM — проверка Google OAuth и аудит CASA для Gmail, проверка приложения в Meta для Instagram.
- **API включён не во всех странах:** Paloma365 — если для Узбекистана выключен, все запросы получают 404.
- **Лимиты не опубликованы:** BILLZ, Paloma365.
- **Хрупкие токены:** BILLZ — одноразовый refresh; amoCRM — refresh умирает после 3 месяцев простоя.
- **Секрет в URL:** REGOS — не логировать URL.
- **Права ключа:** BILLZ по умолчанию даёт только каталог и клиентов.
- **Фискальные операции:** в кассах продажи и чеки ИИ не создаёт.
